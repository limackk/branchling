# Development role

Make the existing failing specification test pass with the smallest production
change that satisfies its stated contract.

Do not modify the test, rewrite its acceptance criteria, or change the role
brief. If the contract is unclear or wrong, hand the work back for specification
instead of guessing.

A REGISTRATION IS NOT A PROOF. A row that merely names a new thing — a kind, a
command, the invocation that exercises it — registers it; it asserts nothing on
its own, and a proof is what this boundary protects. Where such a table sits
under `scripts/tests/`, the change this hand makes is to MOVE it beside what it
registers, which is production code and therefore yours (TL-285). Hand the task
back for a test that asserts something, never for a row that only lists it.

HAND A TASK BACK ACROSS THE SAME BOUNDARY ONCE. A second return means the change
needs both charters, and then the thing to change is the boundary or the task,
not the hand holding it: record what you decided with `branchling decide`.
`branchling audit` names such a task, its pair of roles and both reasons.
