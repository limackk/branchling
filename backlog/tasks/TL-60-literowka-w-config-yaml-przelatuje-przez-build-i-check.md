## Goal

Make the promise "an unknown key fails build" — written in a file that
`worktrail init` itself generates — true, and make the failure look like a
message, not like the tool crashing.

## Context

Measured on 2026-08-31 on a freshly created backlog, after appending one
line, `statusess: [a, b]` (a typo for `statuses`):

| Command | Result |
|---|---|
| `build` | **exit 0, silent** — views rebuilt, default dictionary used |
| `check` | **exit 0, three checkmarks** |
| `query`, `viewer`, `next-id` | pass |
| `stats`, `new`, `serve` | exit 1 + **stack trace** from `config.mjs:258` |

The cause is in `loadConfig(root, opts)`: `strict` defaults to `true`, but is
set per call, and the distribution turned out the opposite of the intent —
`build-backlog.mjs`, all three `check-*` guards, `query.mjs`,
`build-viewer.mjs` and `next-backlog-id.mjs` all call it with
`{ strict: false }`. The effect: the command whose ENTIRE job is to fail when
something is wrong (`check`) is the most lenient, and the ones that do fail
do so with an unhandled exception.

Two sentences, both in files a user reads, are false today:

- `config.yaml` (generated by `init`): "An unknown key fails build."
- `config.mjs`: "An unknown key FAILS — a typo in the dictionary is
  indistinguishable from 'this project just works that way', and costs the
  same as a typo in a CLI flag."

This is the same class the project closed for CLI flags ([TL-25](TL-25-domknij-walidacje-flag-w-5-komendach-tasklog.md)):
a silent no-op looks like it worked. Here it hurts more, because editing
`config.yaml` is the **main act of onboarding** — it is where the user fits
the tool to their project, and where they most need feedback.

**A note so as not to swap one defect for another.** `{ strict: false }` is
sometimes justified in some places: `migrate-prefix` must be able to load the
configuration it is in the middle of fixing, and `next-backlog-id` scans
OTHER branches, where the configuration may be older. The task is to review
each call and justify it individually, not to flip all of them at once.

Scope does NOT include dictionary values in tasks (`status: made-up` still
passes `build` and `check` today) — that is [TL-56](TL-56-slownik-types-w-config-yaml-rozjechal-sie-z-drzewem.md).
Both tasks touch the same read path, so it is worth doing them back to back.

## Pre-flight reading

1. `scripts/config.mjs` — `loadConfig()` (lines ~248–322), `parseConfigYaml()`, `validateConfig()`.
2. Every call to `loadConfig(` outside `config.mjs` — there are twelve, each with its own reason.
3. [TL-25](TL-25-domknij-walidacje-flag-w-5-komendach-tasklog.md) — the same rule for CLI flags.
4. [TL-47](TL-47-brak-backlogu-wychodzi-jako-nieobsluzony-wyjatek-ze-stack.md) — the other half of the problem: an anticipated state should not exit with a stack trace.

## Steps

1. Review every `loadConfig(…, { strict: false })` and record in `## Log` why it stays or why it goes away. The default answer is "goes away".
2. `check` and `build` are meant to fail on configuration problems. This is where the user expects it.
3. Split the two classes of problem: an **error** (unknown key, inconsistent dictionary) fails; a **warning** (e.g. configuration from a future version) passes and is printed. Without this split, every future schema change will be breaking.
4. Replace the exception with a message: file name, line number, key, nearest allowed keys (`statusess` → "did you mean `statuses`?"), and an exit code — no `at …`.
5. Test `scripts/tests/config-strictness.test.mjs`: an unknown key fails `check` and `build`; the message contains no stack trace; deliberately non-strict calls are listed explicitly and justified in the test.

## Acceptance criteria

- [ ] An unknown key in `config.yaml` fails `check` and `build`.
- [ ] No command ends with a stack trace on invalid configuration.
- [ ] The message gives the file, line, key, and a nearest-allowed-key hint.
- [ ] Every remaining `{ strict: false }` has a justification recorded in the code and in `## Log`.
- [ ] The sentences about failing in `config.yaml` and `config.mjs` are true.
