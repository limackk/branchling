A patch release of branchling with three fixes reported from a downstream
repository that drives its backlog with several `branchling run` loops in
parallel worktrees.

## Install or upgrade

```bash
npm install -g branchling@0.1.1
branchling --version
```

## Changes

- **The pre-commit hook works in a linked worktree** (TL-483). Git exports
  `GIT_DIR` to hooks without `GIT_WORK_TREE`, which made git take the backlog
  directory as the top of the work tree. Every `related_docs` path was then
  looked up one directory too deep, and `branchling check` failed in the hook
  while passing by hand. branchling now ignores a `GIT_DIR` that is not paired
  with `GIT_WORK_TREE`. The `unset GIT_DIR` workaround in `.git/hooks/pre-commit`
  is no longer needed.
- **`branchling run` no longer stops on a task that legitimately comes back**
  (TL-484). A task parked by its agent on a new blocker, which the same run then
  closed, was reported as `handed out twice` and the run ended with work left.
  The spin guard now compares the task's `blocked_by` as well, so only a task
  handed out again with nothing changed stops the run. When it does stop, the
  report says how many other tasks are still eligible; under `--json` the new
  `spinGuard` key carries the same fact.
- **`branchling run --stop`** (TL-485). Run from any shell on the same clone, it
  asks every running loop to finish the task it is on and then claim nothing
  new. The report ends with `stopped: asked to stop after <ID>`, `--json` gains
  the `stopRequested` key, and `run --stop --json` answers in a new `run-stop`
  envelope. A loop started after the request is not affected. Stopping a loop
  by killing or freezing it can leave a claimed task that nobody is working.

## Upgrade notes

No change to the task file format or to `config.yaml`. The `--json` envelope of
`run` gains two keys, `spinGuard` and `stopRequested`, both `null` unless the
run ended for that reason.

## Provenance

Published from the signed tag `v0.1.1`. Like 0.1.0, this release was published
