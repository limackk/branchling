A minor release of branchling for two audiences. Teams that ship to more than
one environment can now ask which tasks have reached test and which have reached
production, computed from git refs rather than typed into a field. People
building their own interface on top of branchling get a documented contract:
every field the viewer writes has a command, a task body edit is recorded in
history, and backlog changes stream as JSON lines.

## Install or upgrade

```bash
npm install -g branchling@0.3.0
branchling --version
```

## Changes

### Release tracking across environments

- **`deploy_targets:` in `config.yaml`** (TL-501). A target is selected by the
  paths its commits touch and promotes through ordered stages, each a git ref
  (or several parallel refs). Where a task stands is computed on every call
  with `git cherry`, so a cherry-picked hotfix counts by patch identity and a
  rollback is never contradicted by a stale field.
- **`branchling deploy status`** (TL-502, TL-513) lists, per target, what is
  closed but not on the trunk, on the trunk but not in the first stage, and in
  each stage but not the next. An unresolvable ref reads as unknown, never as
  zero.
- **`branchling deploy record`** (TL-506) moves the ref of a stage declared
  `recorded: true` — store review, a staged rollout, a sign-off — onto an
  annotated tag object carrying the actor and the reason, by compare-and-swap.
- **`branchling check --release`** (TL-503) names seven kinds of traceability
  gap between what a stage holds and what the backlog calls finished.
  `release_gate: report` (the default) prints them; `require` fails on any gap
  `release_gate_accept` does not name.
- **Planned scope** (TL-505, TL-515, TL-516). A task may name the release it is
  planned for in `release:`, from a closed `releases:` list.
  `deploy status --release <name>` compares the plan with what shipped; an
  entry `{name, ref}` is compared with its ref after it has gone out. The
  order of `releases:` is chronological, and only the current release's open
  P0 blocks the last stage.
- **Targets in another repository** (TL-507, TL-512, TL-514). A target may
  declare `repository:`, and a task joins it through its own `target:` field.
  Its tasks are reported as unobservable rather than as false gaps.
- **`branchling show <ID>`** (TL-509) prints the computed facts about one task:
  its deployment state per target and stage, its status on other branches and
  worktrees, and each blocker with its verdict.
- **`branchling doctor`** (TL-508, TL-510) names a deploy ref namespace the
  remote does not fetch, with the exact `git config` line that fixes it, and a
  short ref it cannot resolve.
- **`query --env` / `--not-env`** filter by stage, counted from the same trunk
  `show` and `deploy status` use (TL-517, TL-518).
- **The viewer** has a Release tab with one lane per target and one column per
  stage (TL-504), and filters tasks by planned release (TL-511).

### External interface contract

- **`docs/external-consumers.md`** (TL-525) documents the three channels
  (`--json` per call, `follow --json`, `mcp`), the envelope rules, every
  declared kind and every writing command. A test fails when it and the code
  disagree.
- **`branchling set <ID> <field> <value>`** (TL-521) writes every field the
  served viewer writes, through the same validation and history.
- **`branchling body <ID>`** (TL-523) rewrites a task body from stdin or
  `--body-file` and records it in history like a field edit.
- **`branchling declare releases|deploy_targets`** (TL-522) appends one entry
  to those two configuration keys. Every other key remains a hand edit.
- **`branchling follow --json`** (TL-524) streams one `change-stream` envelope
  per changed task, with `ready` and `heartbeat` lines. It is deliberately not
  an MCP tool (TL-529): a stream is not one tool result.
- **`decide --json` and `where --json`** answer in the standard envelope, with
  `schemaVersion` and a declared `kind` (TL-528).

### Correctness

- **`new` writes caller text literally** (TL-527). A `$'`, `` $` `` or `$&` in
  a title or verification command was interpreted as a replacement pattern and
  could splice the template body into the frontmatter.
- **A verification string from a task document reads back unchanged** (TL-500).
  A command carrying `"` or `\` was written as invalid YAML, and a ` #` after
  an escaped quote was cut off as a comment.

## Upgrade notes

- **`decide --json` refusals renamed two keys.** The refusal carried its name
  under `kind` and its sentence under `message`; `kind` is reserved by the
  envelope, so they are now `refusalKind` and `refusal`, as in every other
  writing command. A consumer reading the old keys must switch. The success
  payloads of `decide --json` and `where --json` keep their keys and gain the
  envelope's `schemaVersion` and `kind`.
- New optional keys in `config.yaml`: `deploy_targets`, `releases`,
  `release_gate`, `release_gate_accept`. All are off unless set. New optional
  task fields: `release` and `target`.
- `follow` is not exposed over `mcp`; run `follow --json` beside it.
- Supported platforms are unchanged: Linux and macOS.
