A minor release of branchling about upgrades and about the machine
interface. A backlog can now state the oldest release that may read it, so
an older copy on a teammate's machine says "upgrade" instead of failing on a
key it does not know, and `doctor` reports every file `init` copied that has
fallen behind this release, with the command that refreshes it. Interfaces
built on `--json` get one envelope for every refusal, the backlog's
vocabularies as data, and the task contents they previously had to read
from files.

## Install or upgrade

```bash
npm install -g branchling@0.4.0
branchling --version
```

A team that shares a backlog upgrades together; see `## Upgrade notes`.

## Changes

### Upgrades are announced, and copied files stay current

- **`requires_version:` in `config.yaml`** (TL-586). A backlog may state the
  oldest release that can read it. A release older than that refuses with
  one message naming both versions and the install command, instead of a
  parse error about an unknown key. `declare` raises the floor itself when
  it writes a key a newer release introduced. A floor below 0.4.0, the
  release that introduced the key, is a problem of its line, because no
  release can enforce it (TL-593), and an empty value states no floor
  (TL-592).
- **`doctor` reports a stale installed skill** (TL-585) by comparing it with
  every version this tool has shipped, and `skills install --refresh`
  replaces it when it holds no edit. A directory or other non-file where a
  skill file belongs is named rather than crashing both commands (TL-594).
- **`doctor` reports a lagging `_template.md` and git hook block** (TL-588).
  `branchling template refresh` adds the frontmatter fields this release
  ships and the template lacks, with their comments, without rewriting any
  line the project wrote (TL-595). `hooks install` replaces a stale block of
  its own in the file's line endings and indentation (TL-601), and for a
  block that was never closed `doctor` names the `hooks print` paste
  instead of a command that would refuse (TL-600).
- **The agent guides route the promotion questions** (TL-584, TL-596,
  TL-597, TL-598). Where `config.yaml` declares them, `branchling
  instructions` names `deploy status`, `deploy status --release`, `check
  --release`, `deploy record` for recorded stages, the `release:` field
  with `declare releases`, and `target:` for a target in another
  repository. A guide line about a command the backlog cannot use is not
  printed.

### The machine interface

- **`branchling vocabulary --json`** (TL-532) answers every vocabulary
  `config.yaml` declares, in declared order. Each status carries whether it
  is archived, whether it needs a reason, and a semantic role (open, active,
  waiting, closed, cancelled); the new optional `status_roles:` map corrects
  a derived role.
- **Refusals are envelopes.** `deploy status --json` with an undeclared
  `--release`, `--target` or `--env` (TL-533), `plan --json` over a plan that
  cannot be read or executed (TL-534), `check --json` without a backlog
  (TL-541), and a query filter or `handoff --to-role` value outside the
  vocabulary (TL-559) each answer an envelope with `ok: false` and a
  `refusalKind`, so a value a person typed is told apart from a malformed
  call.
- **No backlog is exit 1 from every command** (TL-546, TL-547, TL-548), with
  `refusalKind` `no-backlog` in the envelope of the command that was called.
  A `--dir` that is not a backlog is a refusal rather than a stack trace
  (TL-545).
- **Every writing command reports where its actor came from** (TL-544,
  TL-550, TL-537) as `actorSource`: flag, environment, user configuration or
  default. `new` gains `--actor` and `--json`. `decide --require-actor`
  refuses the default agent. A refused actor names the part that is wrong,
  the namespace or the name (TL-590).
- **More of a task is readable without its file.** `show --json` carries the
  verification contract (TL-561) and, with `--body`, the task body (TL-542).
  `log --records --json` returns every ledger record of a task (TL-562), and
  `log --open-questions` lists every question still waiting on an answer
  across the backlog, with its task's priority (TL-536, TL-560).
- **`set --fields`** (TL-543) describes the fields `set` edits as data, and
  an unknown value names the vocabulary it should come from.
- **`query --scope active|archived|all`** (TL-540) chooses which tasks are
  searched before any filter.
- **`plan init --rationale`** (TL-535) starts a plan, so no caller writes
  `plan.yaml` by hand.

### Proofs and the run loop

- **`check --proofs`** runs the project's `closing_contract` once per audit
  instead of once per closing (TL-497), narrows with `--since` by a task's
  own entries (TL-556), audits one task with `--task <ID> --own-only`
  (TL-557), and does not recurse when a contract itself runs `check
  --proofs` (TL-565).
- **`resume` and the run loop's baseline** run the same contract `done` will
  run, and the plain briefing marks the rows that come from `config.yaml`
  (TL-496, TL-558). `handoff --status` on a task that is not in progress is
  refused instead of being ignored (TL-564).

### The viewer

- **The served viewer refuses what `set` refuses**: status and owner, which
  have their own commands (TL-563), and an edit by an unnamed actor
  (TL-551). A save is reported where the user is looking (TL-450).
- **Dashboard metrics** for flow, backlog health and plan progress are
  computed from the same tasks and history, and each count opens the tasks
  behind it (TL-451).

## Upgrade notes

- **New optional keys in `config.yaml`: `requires_version` and
  `status_roles`.** Both are off unless set. A backlog whose configuration
  uses either must be read by 0.4.0 or later, and 0.3.0 and older refuse
  every command on such a file, the pre-commit hook included. **A team that
  shares a backlog should upgrade together**, and should set
  `requires_version: 0.4.0` once it has, so the next release that adds a key
  can tell an older copy to upgrade instead of failing. Releases up to 0.3.0
  do not know `requires_version` and cannot read that message.
- **Exit codes.** Commands that answered a missing backlog, or a `--dir` that
  is not one, with exit 2 and `refusalKind` `usage` now exit 1 with
  `no-backlog`: among them `take`, `next`, `set`, `handoff`, `ask`, `decide`,
  `body`, `run`, `deploy`, `declare`, `seed`, `import` and `skills install`.
  `where` exits 1 for a named directory that is not a backlog. A query
  filter or `--to-role` value outside the vocabulary exits 1 with
  `unknown-value` rather than 2.
- **`deploy status --json` and `plan --json`** carry `ok`, and answer a
  refusal on stdout instead of an empty stdout.
- **`doctor` may show new rows** on an existing backlog: a stale skill, a
  `_template.md` that lacks this release's fields, or a stale hook block.
  Each names the command that refreshes it; none of them is a failure.
- **Packaged skill files are named with `/` on every platform**, as
  `skills install --refresh <file>` expects them.
- Supported platforms are unchanged: Linux and macOS.
