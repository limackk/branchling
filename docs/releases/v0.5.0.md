A minor release of branchling about running a backlog with several agents
at once, and about importing from Jira. A plan wave whose open work is
claimed in another tree, or closed on a branch not yet merged, is reported
as waiting rather than empty, and `next`, `run` and `plan` agree on it.
`next` can say what it would hand out without claiming it and honours a stop
request, and a closed task can be reopened with a reason. Jira becomes the
second import source, and a merged task's proof can be posted to its Jira
ticket. Refusals draw one line across commands: a value a person typed is
exit 1 with `unknown-value`, and exit 2 stays for a call built wrong.

## Install or upgrade

```bash
npm install -g branchling@0.5.0
branchling --version
```

A 0.4.0 backlog reads unchanged; see `## Upgrade notes`.

## Changes

### Plans and loops with several agents

- **A waiting wave is not an empty one** (TL-683, TL-707, TL-729, TL-734,
  TL-741). `next --plan` exits 3 with `wave-claimed-elsewhere` or
  `wave-awaits-merge` instead of `nothing-to-take`; `run --plan` acts on
  both, and `run --plan --json` names the wave as `planWaiting`.
- **`--spill`** with `--plan` lets `next` and `run` draw from the next wave
  with open work while the active one waits; blockers and conflict groups
  still hold, and `run --dry-run` projects the same way (TL-707, TL-731,
  TL-743, TL-744).
- **`plan` agrees with the run** (TL-645, TL-664, TL-666). It names a wave
  held shut by tasks no unattended run will take, and why, withholds a task
  another tree has claimed, and holds a wave on an open question whatever
  the task's status. The viewer shows a held wave the same way (TL-660).
- **`new --wave-hint <name>`** (TL-689) writes the wave into the task's own
  file as `wave_hint:`, so follow-ups filed on parallel branches do not
  conflict in plan.yaml; `plan place` appends them to their waves. The
  task-execution guide names this form when a plan exists.
- **`plan add` and `plan move` take `--before` or `--after <wave>`** for the
  wave they create (TL-677, TL-712).
- **`next --dry-run`** names the task it would hand out and writes nothing
  (TL-644). **`next` honours `run --stop`** until `run --stop --clear`
  withdraws the request (TL-697).

### Taking, closing and reopening

- **`take --reopen --reason "…"`** withdraws the closing of a task rejected
  in review and claims it again (TL-714). The closed refusals of `take`,
  `handoff` and `body` print that command (TL-737, TL-742); `take` on your
  own unmerged closing names `resume` instead (TL-684).
- **`done` with no terminal parks a `manual:` entry** (TL-699, TL-736). When
  every automatic entry passed, the task moves to `awaiting_vouch_status`
  with a record, and `done` exits 3. Under `--json` it still refuses with
  `manual-needs-person`; without the key it refuses as before.
- **Files are attributed to a task by the commit title only** (TL-614,
  TL-626, TL-627): an id in a commit body no longer claims that commit's
  files for `query --modified-file`, `done`'s capability record or `deploy
  status`, and a mistyped title range counts only its endpoints. A
  verification that runs a changed script directly counts as executing it
  (TL-679). `check --proofs` on an in-progress task names `done --dry-run`
  (TL-685).
- **Fenced code is not criteria** (TL-669, TL-709, TL-728, TL-733): a fenced
  heading or checkbox is never read or ticked as a criterion.
- **The reserved actor `unknown` is refused as the author of an act** by
  `set`, `take`, `next`, `handoff` and the viewer (TL-569, TL-628, TL-671).
  `check --reasons` reports an `unknown` reason as an outside change only
  under an observing source (TL-663).
- **`new` names an open task whose title it nearly repeats** and still
  creates the task; under `--json` as `nearDuplicates` (TL-649).

### Query

- **`--ids <id,id,…>`** and **`--conflict-group <g>`** select exactly those
  tasks and combine with other filters (TL-680, TL-687).
- **`--owner` ending in `*` matches a prefix, and `--worktrees`** reads every
  sibling worktree, so an uncommitted claim there is found (TL-700). A task
  only on another branch is named only when the criteria could match it
  (TL-715). `--text` accepts a value that begins with a dash or spells a
  flag (TL-691, TL-718).

### Import from Jira, and proofs back to it

- **`import --from jira`** (TL-581) reads Jira search responses on stdin:
  descriptions converted from Atlassian Document Format, status mapped by
  category or `--status`, a browse-URL marker written, and a re-run skipping
  what is imported. `--priority <from>=<to>` maps priorities, refusing an
  unknown target before anything is written (TL-641).
- **`branchling jira-proof --base <ref>`** (TL-582) prints one comment per
  Jira ticket whose task entered a closed status in the range, with the
  checks its verification ran. It makes no network request;
  `examples/jira-proof.yml` in the repository is a CI job that posts them.
- **A GitHub import names the step that retires the source issues**, with
  each issue's state in `created[]` (TL-580), and names milestones among
  what it does not bring over (TL-577). An imported description heading
  cannot pose as one of the task's own sections (TL-640).

### Refusals, help and the machine interface

- **A typed value outside a vocabulary is `unknown-value`, exit 1**, with
  `rejected` and `declared`, for `next` and `run` filters, `handoff
  --status` and `--to-owner` (TL-574) and `new` (TL-630). An archived
  status to `handoff` or `release --status` is `archived-status`, exit 1
  (TL-635, TL-675).
- **Envelopes.** Every refusal of `new --json` answers in `task-new`
  (TL-568); `hooks print|install|uninstall --json` and `skills install
  --json` answer in kinds of their own (TL-567).
- **An unknown command or flag suggests the nearest one** (TL-701), such as
  `--text` for `--grep` and `done --dry-run` for `verify`. Every `--help`
  ends with an exit line (TL-572), `help --json` describes `<from>=<to>`
  flags as pairs (TL-693, TL-719), and counts never read `field(s)`
  (TL-616, TL-637).

### doctor, hooks, skills and the viewer

- **`doctor` reports an uncommitted closing and an interrupted merge**, and
  `resume` puts an uncommitted closing first (TL-688). Its printed fixes
  carry the `--dir` it was run with (TL-615, TL-631), as a bare word cmd
  reads back on Windows (TL-763).
- **A file or dangling link where a skill or `.claude/skills` belongs** is
  reported by `skills install` and `doctor` with the path to move aside,
  not a crash (TL-603, TL-632, TL-633, TL-634, TL-668, TL-692).
- **The hook block** repair keeps the user's lines after an unclosed block,
  a hook that only mentions the marker is foreign, marker indentation is
  kept, and `hooks uninstall` reports no removal it did not make (TL-609,
  TL-610, TL-622, TL-639).
- **The guides** from `branchling instructions` describe the release line
  truly without a local target and name the accepted gaps and the stages
  that take `--ref` (TL-606, TL-608, TL-619, TL-620, TL-651, TL-607).
- **The viewer** names which half of an actor is wrong, as agent profiles
  do (TL-605), and carries no reason prompt no write can reach (TL-566).

### Under the hood

- Task records are read in filename order on every filesystem (TL-643), a
  Windows lock waits out a pending release (TL-765), and the suite holds
  under forced colour and a symlinked temporary directory (TL-760).

## Upgrade notes

- **No new `config.yaml` keys.** A 0.4.0 backlog reads unchanged, and a
  `requires_version: 0.4.0` floor needs no change. A task that `new
  --wave-hint` writes is read by 0.4.0 without complaint, but 0.4.0 ignores
  its `wave_hint:` and has no `plan place`, so teams that share a backlog
  and file hinted tasks should upgrade together.
- **Exit codes.** A value outside a vocabulary given to `next`, `run`,
  `handoff`, `release --status` or `new` exited 2; it now exits 1 with
  `unknown-value`, or `archived-status` for an archived status. Exit 2
  remains for an unknown flag or a missing value.
- **New exit 3 answers.** `next --plan` on a waiting wave answers
  `wave-claimed-elsewhere` or `wave-awaits-merge` where it answered
  `nothing-to-take`, and `next` under a stop request answers
  `stop-requested` instead of claiming. `done` exits 3 when it parks a task
  in `awaiting_vouch_status`; without that key it exits 1 as before.
- **Envelopes.** `new --json` answers every refusal on stdout. `hooks
  --json` and `skills install --json` add `schemaVersion`, `kind` and `ok`
  around the keys they printed before.
- **`--actor unknown` is refused** by `set`, `take`, `next`, `handoff` and
  the viewer; name a namespaced actor instead.
- **`doctor` may show new rows**, `closing not committed` and `interrupted
  merge`, both warnings.
- **Platforms.** Linux and macOS are supported. Windows is tested in CI but
  is not yet declared supported (TL-456).
